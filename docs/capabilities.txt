CAPABILITY 1
Name: take_declaration
Used at: Declared
Rail: Voice
What you send it: Live caller audio to the agent's botId
What comes back: Transcript, plus event, dates, ceiling and group size as typed extraction fields
When it fails: A constraint arrives missing or corrupted
What it must never do: Invent a value the caller did not say
What exists today: Gnani Agent Builder single-prompt agent; STT Realtime WebSocket (/api/STT/stt-websocket, base https://api.vachana.ai); Post-call Data Extraction with typed fields; Inverse Text Normalisation. We built and called this agent on the platform.
Build Status: Exists

CAPABILITY 2
Name: confirm_constraints
Used at: Declared to Verified
Rail: Voice
What you send it: The four captured values, read back aloud
What comes back: Caller confirmation or correction
When it fails: The caller confirms a value the agent captured wrongly. On a live call ours read back Rs 10,000 after the caller said "eight to ten thousand, ideally eight", accepted "yes I do need it" as confirmation, and closed the call as declaration_complete.
What it must never do: Treat silence or vague assent as confirmation
What exists today: Prompt-level readback; Disposition enum returned via /Platform/Get_Conversation_Stats
Build Status: Exists

CAPABILITY 3
Name: verify_declaration_intent
Used at: Declared to Verified
Rail: Voice
What you send it: Transcript plus the captured values
What comes back: Per-field confidence, and a flag wherever the caller's own words contradict the captured value
When it fails: No endpoint exists to call
What it must never do: Let a ceiling reach a fund block on one unchallenged confirmation
What exists today: Nothing. Extraction returns values with no confidence signal, so a wrong value arrives tagged declaration_complete exactly like a correct one.
Build Status: Must Build

CAPABILITY 4

CAPABILITY 6
Name: create_claim_block
Used at: Verified
Rail: Payments
What you send it: POST /api/v1/public/subscriptions/ot with customer_id, plan_details.amount set to the declared ceiling, and validity_days; then POST /api/pay/v1/orders/{order_id}/payments with mandate_info.request_type CREATE_MANDATE
What comes back: subscription_id, order_id, status CREATED, and a challenge_url (upi://mandate?...)
When it fails: The caller never approves and the subscription stalls at CREATED
What it must never do: Create a block before the ceiling has been confirmed aloud
What exists today: UPI One-Time Mandate. Funds are blocked in the customer's own account, up to 60 days validity, Rs 1 lakh default cap, one UPI PIN entry at setup.
Build Status: Exists

CAPABILITY 9
Name: capture_on_win
Used at: Captured
Rail: Payments
What you send it: POST /api/v1/public/presentations with subscription_id and an amount at or below the stored ceiling
What comes back: presentation_id, status PENDING, then the Subscription charged webhook
When it fails: A Presentation failed webhook leaves a won slot with no money behind it

CAPABILITY 10
Name: release_losing_claims_at_scale
Used at: Allocated to Confirmed
Rail: Payments
What you send it: Every losing claim's subscription_id, in bulk, at the moment allocation resolves
What comes back: Confirmed release of each block within seconds, against a stated latency SLA
When it fails: Losers' money stays frozen and they cannot declare into the next window
What it must never do: Hold a losing claimant's funds a moment longer than the allocation needs
What exists today: The One-Time Mandate overview documents releasing a block, but the OT direct-execution integration guide exposes no release endpoint, no bulk operation and no latency commitment. ASBA, the closest national-scale analogue, unblocks in 24 to 48 hours.
Build Status: Must Build

CAPABILITY 11
Name: contingent_basket_mandate
Used at: Verified, Allocated
Rail: Payments
What you send it: One authorisation covering N mutually exclusive claims, each with its own ceiling
What comes back: A single block against which at most one claim captures, the rest voiding the instant allocation resolves
When it fails: A user declaring three options has three separate blocks, freezing three times their ceiling
What it must never do: Capture more than one claim from a single basket
What exists today: Nothing in this shape. OTM allows one successful capture and the mandate closes after capture. UPI Reserve Pay allows multiple debits against one reserve until exhausted, which drains a pool rather than voiding alternatives.
Build Status: Must Build

CAPABILITY 12
Name: atomic_group_capture
Used at: Captured
Rail: Payments
What you send it: N subscription_ids held by N different payers, as one all-or-none transaction
What comes back: All captures succeed, or none do and every block releases
When it fails: 19 of 23 capture and four friends are orphaned at the same event
What it must never do: Seat part of a group that declared as one
What exists today: Nothing. Each presentation is independent and there is no cross-subscription transaction primitive.
Build Status: Must Build
